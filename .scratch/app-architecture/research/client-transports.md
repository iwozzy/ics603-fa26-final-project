# Client transports: HTTP, WebSockets, and progress notifications

Research for **Research HTTP and WebSocket transport trade-offs** (tracker context: `.scratch/app-architecture/issues/02-research-client-transports.md` in the main checkout). Investigated 2026-11-06 against primary specifications and official platform/framework documentation. This report supplies evidence and decision criteria; it does **not** choose the application's transport contract, framework, job system, or hosting provider. Framework examples describe capabilities, not dependencies already selected by this project.

## Finding: the socket-overhead hypothesis needs a narrower claim

WebSockets can reduce per-message overhead and remove polling latency for frequent bidirectional messages on an established connection. The broader claim that ordinary HTTP repeatedly pays connection setup costs is incorrect: HTTP/1.1 defaults to persistent connections; HTTP/2 supports concurrent exchanges and compressed headers on one connection. HTTP/3 maps HTTP onto QUIC, with stream multiplexing and per-stream flow control. Connection reuse still depends on actual clients, proxies, idle timeouts, and negotiation. [HTTP/1.1 §9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3), [HTTP/2 §§2, 4.3, 5](https://www.rfc-editor.org/rfc/rfc9113.html#section-2), [HTTP/3 §§1–2](https://www.rfc-editor.org/rfc/rfc9114.html#section-1)

The original WebSocket protocol starts with an HTTP/1.1 Upgrade handshake, then exchanges framed messages. A small unextended frame with payload at most 125 bytes has a two-byte base header; client frames also carry a four-byte masking key. Those figures exclude TCP/IP, TLS, heartbeats, application envelopes, and reconnects. They do not establish an end-to-end speedup. [RFC 6455 §§1.3, 5.2–5.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.2)

WebSockets are not universally a separate TCP connection: RFC 8441 defines Extended CONNECT on an HTTP/2 stream, and RFC 9220 adapts that mechanism to HTTP/3. Support must be checked through the complete browser/native-client, edge, proxy, and Python-server chain; specification support is not deployment support. [RFC 8441 §§3–5](https://www.rfc-editor.org/rfc/rfc8441.html#section-3), [RFC 9220 §3](https://www.rfc-editor.org/rfc/rfc9220.html#section-3)

**Inference for this app:** occasional search queries, follows, and watch-status changes may save bytes over a warmed socket, but that does not demonstrate a useful latency or operating-cost improvement. Query processing, TMDB calls, image transfer, and model inference need separate timing. Conversely, a demonstrated need for sustained interactive bidirectional traffic would make WebSockets more compelling. No benchmark was performed here.

## Semantics and workload boundaries

HTTP supplies method semantics, status codes, conditional requests, and a common authentication framework. GET is safe; PUT and DELETE have idempotent semantics; POST is not inherently idempotent. A 202 response means processing was accepted, not completed, and its representation ought to identify a status monitor. Caching of personalized results requires deliberate controls rather than an assumption that GET is publicly cacheable. [HTTP Semantics §§9, 11, 13, 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9), [HTTP Caching §3](https://www.rfc-editor.org/rfc/rfc9111.html#section-3)

The following are **design implications**, not decisions or required endpoint names:

| Workload | What matters for an HTTP candidate | What must be justified for a WebSocket candidate |
| --- | --- | --- |
| Cast & crew/movie search; timeline pages | Request/result shape, pagination, stale-query cancellation, latency, private caching. Debounce typing independently of transport. | Request correlation, deadlines, cancellation, error mapping, and ignoring stale responses become explicit protocol work. Frequency and latency measurements must warrant it. |
| Follows; watch status | Prefer operations that express desired state where practical; distinguish committed results from pending requests. Retry behavior still needs thought. | Messages require durable acknowledgement and duplicate handling if retried after an uncertain disconnect; socket delivery is not proof of database commit. |
| Semantic storyline search | Embedding/retrieval latency and cancellation dominate the choice of one result versus streamed partial results. The search algorithm does not require a socket. | Useful only if incremental results or interactive exchanges improve the experience enough to warrant the stream contract. |
| Photo/note extraction | Distinguish upload acceptance, extraction acceptance, progress, editable review results, and persisted records. A status/result resource can outlive the initiating request. | Progress does not imply that the original request or socket must remain open. Define job identity and recovery before choosing notification delivery. |
| Future release notifications | Delivery while the app is closed is a platform-notification concern. | A foreground connection cannot substitute for platform background delivery. |

HTTP does not automatically provide exactly-once commands. If a connection drops after a write commits but before acknowledgement, a retry can be ambiguous. A WebSocket request ID alone also does not solve this. **Candidate application invariant:** where duplicate effects matter, retain a deduplication key/result for an agreed interval and scope it to the authorized user and operation; acknowledge only the chosen acceptance/commit boundary. This is application design inferred from HTTP retry semantics and connection failure behavior, not a capability granted by either transport. [HTTP Semantics §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## Photo uploads: binary transfer is separate from progress

HTTP multipart forms can carry a file with metadata; ASGI supports delivering large HTTP request bodies in chunks. FastAPI's `UploadFile` demonstrates a spooled file interface instead of requiring every upload to occupy memory completely. WebSocket's browser API also accepts binary `Blob`/buffer data, so binary transfer does not require base64. [RFC 7578 §4](https://www.rfc-editor.org/rfc/rfc7578.html#section-4), [ASGI request events](https://asgi.readthedocs.io/en/latest/specs/www.html#request-receive-event), [FastAPI files](https://fastapi.tiangolo.com/tutorial/request-files/#file-parameters-with-uploadfile), [WebSocket interface](https://websockets.spec.whatwg.org/#the-websocket-interface)

**Inference:** a large photo amortizes modest request headers. Sending it through a socket introduces a need to define file boundaries, metadata, size limits, admission, cancellation, completion, and restart/resume behavior. Sharing one ordered message channel with latency-sensitive commands also requires deliberate scheduling. HTTP uploads are not automatically resumable either; resumable chunks or direct storage uploads would be separate contracts to investigate if measured photo sizes and failure rates warrant them. Upload progress (bytes transferred) and extraction progress (work completed) must be presented separately.

There is a concrete native-platform constraint: Apple's background `URLSession` transfer facility supports HTTP/HTTPS only, and background uploads must originate from files; uploads from data or streams fail after the app exits. A foreground socket upload does not acquire those guarantees. [Apple background transfers](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)

## Progress notification alternatives

| Candidate | Fit and costs | Recovery obligations |
| --- | --- | --- |
| Periodic HTTP status polling | Simple request/result interface when work is occasional or seconds of delay are acceptable. Poll only while useful, with backoff and a terminal stop condition. | A stable authorized operation ID and current status allow recovery without replaying each intermediate update. |
| HTTP long polling | Server holds a status request until change or timeout; can reduce empty responses while retaining HTTP semantics. It still holds server resources and repeatedly reissues requests. | Cursor/version, timeouts, cancellation, retry/backoff, and current-state recovery. ASGI explicitly supports a held long-poll response. |
| Server-sent events (SSE) | One-way UTF-8 event stream over HTTP. Browser `EventSource` reconnects and can send `Last-Event-ID`; server events may specify `id` and `retry`. Commands/uploads still need another request path. | Event retention and replay are server responsibilities. If history expired, return/resynchronize a current snapshot. Automatic reconnect is not durable delivery. |
| WebSocket | Full-duplex text/binary messages; attractive when actual bidirectional interaction or a shared live channel is needed. | Reconnect policy, resubscription, cursor/replay or snapshot recovery, request correlation, and acknowledgements are application protocol work. |

Sources for the mechanisms above: [ASGI HTTP connection scope](https://asgi.readthedocs.io/en/latest/specs/www.html#http-connection-scope), [SSE processing and event IDs](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events), [WebSocket framing and reconnect backoff](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.2.3). Polling/long-polling trade-offs and recovery contracts are analysis, not specification mandates.

For an illustrative polling interval `T` and `A` active pollers, steady polling produces approximately `A/T` status requests per second. If completion is uniformly distributed within an interval, average added detection delay is `T/2`. These are simple estimates, excluding backoff and terminal requests, not measurements. They make the delay/cost trade-off concrete before requiring an always-open channel.

Browser `EventSource` exposes a URL and credentials option, not arbitrary request headers. Browser `WebSocket` exposes a URL and subprotocols, also not arbitrary headers. Token-header schemes that work in native HTTP clients therefore need an explicit browser solution: cookies with the relevant origin/CSRF controls, an appropriately designed authenticated stream client, or another bounded credential exchange. A fetch-based SSE parser would also need its own reconnect/resume handling. [EventSource interface](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface), [WebSocket interface](https://websockets.spec.whatwg.org/#the-websocket-interface)

## Authentication, authorization, backpressure, and reconnect

OWASP's first-party WebSocket security guidance calls for WSS, an explicit handshake Origin allowlist, ongoing session validation, per-action authorization, connection/message limits, and message-level observability. Cookies may accompany browser handshakes; ordinary HTTP CORS configuration alone is not the WebSocket authorization contract. Long-lived sessions need an expiration/logout policy. Avoid long-lived tokens in URLs, which can appear in logs. Native clients require real credentials as well: Origin is a browser defense, not proof of identity. [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html#authentication-and-authorization)

The standard browser socket API exposes `bufferedAmount` but no awaited stream-style send/read backpressure contract. It can close when the send buffer cannot accept more data. Server libraries have their own limits: Uvicorn exposes incoming message-size/queue bounds and ping interval/timeouts, with availability varying by WebSocket implementation. [WebSocket API sending](https://websockets.spec.whatwg.org/#dom-websocket-send), [Uvicorn settings](https://uvicorn.dev/settings/#implementation)

**Design implications:** bound per-client queues and simultaneous work, coalesce superseded progress updates, and disconnect or resynchronize slow consumers. Do not silently drop terminal results unless they remain retrievable. Validate Pydantic boundary models per incoming message, not only when opening a connection. A socket keepalive indicates connection liveness, not that an extraction or transaction succeeded.

After abnormal closure, RFC 6455 recommends randomized reconnect delay followed by increasing backoff. It does not supply business-operation replay. **Candidate recovery invariant:** foreground/reconnected clients first reconcile current authorized state, then subscribe from a cursor if retained history is required. Choose between latest-status recovery and full event replay based on product needs; not every progress percentage deserves durable storage. [RFC 6455 §7.2.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.2.3)

## Mobile lifecycle

iOS normally transitions background apps toward suspension, with specific facilities for limited background work. Android Doze suspends ordinary app network access and defers background work; Google's guidance recommends FCM for downstream messaging rather than each app maintaining a persistent connection. Platform push facilities are a separate option for future notifications, not a guarantee of immediate job-progress delivery. [Apple lifecycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle), [Android Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)

**Inference:** web and native adapters must handle sleep, offline periods, process loss, token expiry, and network changes. SSE and WebSocket streams should be treated as replaceable foreground connections. Persist or recover operation identity as required by the chosen product behavior; query current state on return. Measure battery and radio/network use under realistic lifecycle transitions before claiming an idle socket saves resources over bounded polling.

## Async Python is not durable execution

`asyncio` uses cooperative scheduling: while a task awaits I/O, other tasks can run. ASGI describes both HTTP and WebSocket applications, so either transport can use asynchronous I/O. CPU work that does not yield still needs isolation or another execution strategy. [Python 3.13 tasks](https://docs.python.org/3.13/library/asyncio-task.html#task-object), [ASGI HTTP/WebSocket](https://asgi.readthedocs.io/en/latest/specs/www.html)

Starlette explicitly describes response background tasks as **in-process**, run after the response is sent. Neither such a task nor `asyncio.create_task` constitutes a persisted job ledger or recovery policy. A process/container crash can lose its running work. Durable execution requires a separate design for persisted acceptance/state, recoverable inputs, worker ownership, retries, timeouts, cancellation, and duplicate effects. [Starlette background tasks](https://starlette.dev/background/), [Python task scheduling](https://docs.python.org/3.13/library/asyncio-task.html#creating-tasks)

Even choosing a queue does not settle this: Celery documents acknowledgement/redelivery trade-offs, default acknowledgement before execution, and exceptions around worker termination even with late acknowledgement. This is evidence for defining the required crash/retry semantics, **not** a recommendation to adopt Celery. Client transport and durable execution are separate axes. [Celery tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html)

## Proxies, processes, and Docker

- For HTTP/1.1 WebSocket proxying, Nginx requires explicit Upgrade/Connection forwarding. Its documented default closes a proxied connection after 60 seconds without upstream data; configure read timeouts or appropriate pings. Actual host/CDN limits still need verification. [Nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html)
- SSE can be delayed by response buffering: Nginx enables proxy response buffering by default and exposes `proxy_buffering`/`X-Accel-Buffering`. Upload request buffering is separately controlled and can consume temporary disk. Test both directions at the real edge. [Nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering)
- A connection belongs to its serving process. FastAPI's in-memory connection-manager example explicitly works only for one process and while that process runs. **Inference:** if a job completes elsewhere, notification routing needs shared state or interprocess delivery; sticky routing alone does not make jobs/results durable. A single initial process may avoid that mechanism until scaling/reliability requirements demand it. [FastAPI connections](https://fastapi.tiangolo.com/advanced/websockets/#handling-disconnections-and-multiple-clients)
- Docker stop sends the configured termination signal, normally SIGTERM, then SIGKILL after the grace period. Uvicorn separately has a graceful-shutdown timeout. **Inference:** align these windows, drain connections, reject new work at the appropriate point, and recover unfinished operations after replacement. Docker does not preserve sockets across process replacement. [Docker stop](https://docs.docker.com/reference/cli/docker/container/stop/), [Uvicorn timeouts](https://uvicorn.dev/settings/#timeouts)

The deployment investigation still must establish HTTP versions on **each hop**, maximum stream lifetime, idle timeouts, buffering, body/message limits, termination behavior, and connection quotas. ASGI's ability to represent HTTP versions does not imply every server or proxy negotiates all of them.

## Measurements and decisions to carry forward

Before selecting transports, compare equivalent behavior and authentication through the same intended deployment:

1. Measure cold and warm request latency, negotiated HTTP version, connection reuse, bytes including headers/framing/heartbeats, and time spent in database/provider/model calls. Compare realistic intermittent sessions as well as bursts; do not compare cold HTTP with an already-warmed socket.
2. Record expected concurrent users/tabs, query and command frequency, photo sizes, active extractions, progress frequency, acceptable update delay, p50/p95 completion latency, and failure rate. These inputs determine whether a few polls or a stream offers meaningful value.
3. Measure per-connection memory, CPU, open descriptors, queue growth, proxy capacity, and reconnect bursts during deployment. Use slow consumers and concurrent photo uploads. Track message-level latency/errors and job IDs in Logfire or equivalent instrumentation without credential/image logging.
4. Exercise lost acknowledgements, offline/reconnect, expired cursors, duplicate commands, expired sessions/logout, worker/container death, background suspension, and foreground recovery. Include iOS background upload and Android Doze tests when native adapters exist.

**Boundary candidates for human decision:** keep application operations and their validated results independent of HTTP request objects and WebSocket frames; place transport encoding/session lifecycle in inbound adapters. Frontend application code can depend on capabilities such as search, set-follow-state, upload-photo, and observe-extraction rather than one global socket. Identity, errors, operation IDs, and result recovery must agree across adapters. These are ports-and-adapters design inferences consistent with the user's preference, not decisions established by transport standards.

The costly early questions are required delivery/acceptance semantics, authentication across browser/native clients, cancellation versus durable continuation, and whether clients must recover results after leaving. A concrete message catalog, HTTP/3 rollout, replay broker, and resumable-upload implementation can wait until those answers or measurements justify them. A mixed design remains viable: HTTP commands/uploads with polling or SSE progress, or a WebSocket for a proven live interaction need, can call the same application ports. This report leaves that choice open.
