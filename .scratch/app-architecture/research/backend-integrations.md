Related tracker question: **Research feasibility of the proposed backend integrations** (`.scratch/app-architecture/issues/03-research-backend-integrations.md` in the main checkout). The research branch starts at `3293b22`. ## Assessment

The proposed async Python integrations have plausible technical paths, but end-to-end compatibility is unproved. The unidentified LLM Gateway is an explicit prerequisite: its identity, protocol, authentication, limits, model capabilities, and data handling are unknown. The other material prerequisite is permission for TMDB use in this AI-enabled product: the current API terms contain broader AI restrictions than the FAQ's noncommercial summary suggests. The sections below separate documented behavior from architectural implications and verification work.

No model, embedding model, database driver, ORM, vector store, deployment host, or final production stack is selected here. No credentials, accounts, API calls requiring authentication, prototypes, or dependency installation were used.

## Async Python and validation boundaries

Python's event loop executes tasks cooperatively; blocking computation on its thread delays all other tasks. Async syntax alone does not make image processing, synchronous database calls, or SDK calls nonblocking. Python documents executors for blocking work. **Implication:** use asynchronous I/O through each adapter and deliberately isolate expensive image decoding/resizing or other blocking work. [Python 3.13 asyncio development guidance](https://docs.python.org/3.13/library/asyncio-dev.html)

`TaskGroup` and timeouts use cancellation; cleanup belongs in `try/finally`, and suppressing `CancelledError` can break structured concurrency. An ordinary task exists in the process's event loop. **Implication:** define deadline ownership and cleanup for pooled connections, HTTP streams, and uploads. A task scheduled inside a request process is not evidence of crash recovery or durable execution; that is a separate product requirement. [Python 3.13 tasks and cancellation](https://docs.python.org/3.13/library/asyncio-task.html)

Current Pydantic documentation requires Python 3.10+, and Pydantic AI requires 3.11+, so the declared Python 3.13 baseline clears those documented minima. This does not prove a complete dependency set works in the eventual container: pinned releases, provider extras, native wheels, system libraries, OS and CPU architecture still need a build check. Pydantic uses Rust-based `pydantic-core`; Pydantic AI offers a slim installation with selected extras. [Pydantic installation](https://docs.pydantic.dev/latest/install/), [Pydantic AI installation](https://ai.pydantic.dev/install/)

Pydantic normally coerces compatible inputs, and models ignore extra fields unless configured otherwise. Strict validation can be enabled by field, model, or validation call, with some differences between Python-object and JSON validation. `model_construct()` bypasses validation. **Implication:** consciously specify coercion, extra-field policy, size limits, nullability and serialization at client, provider, and AI output boundaries. Preserve tolerable upstream additions in provider adapters rather than accidentally treating every provider field as a public contract. Do not use validation bypasses on external input. [Models and extra data](https://docs.pydantic.dev/latest/concepts/models/), [Strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/)

**Architectural inference:** successful schema validation establishes shape and declared constraints, not whether an extracted title identifies the intended movie, whether a user owns a record, or whether an operation is permitted. Matching, authorization, invariants, and human review need application-level rules beyond boundary models.

## Pydantic AI and the unidentified LLM Gateway

Pydantic AI separates model interfaces from providers. Official guidance supports listed providers, other compatible APIs, or a custom model for an otherwise unsupported API. Its separately branded **Pydantic AI Gateway** is a specific service; the project's phrase “LLM Gateway” does not establish that it is that service. A configurable base URL is not proof of protocol or feature compatibility. [Models and providers](https://ai.pydantic.dev/models/overview/)

Pydantic AI distinguishes tool output, native JSON Schema output, and prompted output. Tool output sends a schema as a tool definition; native output needs model/API support and can impose restrictions; prompted output relies on the model following the schema, even when JSON mode ensures syntactically valid JSON. Pydantic AI validates structured results, but that does not create provider-native guarantees. Streaming structured output additionally depends on the route's streaming capabilities. [Output modes and streaming](https://ai.pydantic.dev/output/)

The following is a verification agenda, **not a claim about the unknown gateway**:

| Evidence needed before binding the adapter | Consequence if missing or different |
| --- | --- |
| Gateway identity, owner, versioned documentation, base URL, supported API/interface and auth/header requirements | Cannot choose an existing provider/interface or know whether a custom model is necessary. Do not assume OpenAI compatibility, a particular endpoint family, or an available key. |
| Exact route/model capabilities: text, image input transport and MIME/size limits, tool calling, native JSON Schema subset and JSON mode | Determines feasible photo extraction and output mode; a model name alone does not establish what the gateway forwards. |
| Streaming format, streamed tool arguments, refusal/truncation/error shapes, usage reporting and cancellation behavior | Determines parser behavior, error contracts, accounting and whether interrupted requests may still incur cost. |
| Context/output ceilings, concurrency, requests/tokens per window, daily or monetary limits, reset semantics and `429` behavior | Determines admission control, input bounds, backpressure and user-visible retry behavior. No numeric quota is currently verified. |
| Gateway, SDK and application retry layers; timeout behavior; idempotency or request IDs | Avoids accidental request multiplication and ambiguity after disconnects. A local timeout is not proof the upstream request stopped. |
| Retention, training/data reuse, region/subprocessors, uploaded-image handling, logging and deletion controls | Determines which user notes/photos can be sent and what must remain excluded from telemetry. |
| Embeddings endpoint availability and its actual contract | Semantic search cannot assume that a gateway exposing generation also exposes embeddings. No embedding model is chosen. |

Pydantic AI has agent-run usage limits and output/HTTP retry mechanisms. **Implication:** set explicit budgets and test the selected release's retry behavior together with the actual gateway/SDK. A per-run request cap does not implement a fleet-wide account quota or prove a billing ceiling. A global quota needs coordinated admission/accounting across workers, with behavior chosen for unavailable accounting. [Agent usage limits](https://ai.pydantic.dev/agents/#usage-limits), [Retry mechanisms](https://ai.pydantic.dev/retries/)

The decisive next evidence is the gateway's official documentation followed by a small, separately authorized compatibility check against its real endpoint. This investigation did not infer its protocol, inspect credentials, or select a route/model.

## Neon/Postgres access and pooling

Async Python access is feasible without deciding the persistence library: Psycopg documents async connections and async pools, while asyncpg implements the Postgres protocol for asyncio. Psycopg serializes operations sharing a connection, and their cursors share transaction state. If an ORM is later chosen, SQLAlchemy documents a separate `AsyncSession` for each concurrent task and warns against implicit I/O on attribute access. These are alternatives and constraints, not selections. [Psycopg concurrent operations](https://www.psycopg.org/psycopg3/docs/advanced/async.html), [Psycopg pools](https://www.psycopg.org/psycopg3/docs/advanced/pool.html), [asyncpg](https://magicstack.github.io/asyncpg/current/), [SQLAlchemy async sessions](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks)

Neon's pooled endpoint uses PgBouncer transaction pooling: a backend connection returns after a transaction. Current documentation lists up to 10,000 client connections, but actual Postgres connections depend on compute size and remain shared across per-role/database pools. That number is not simultaneous query throughput. Session-level settings, `LISTEN`/`NOTIFY`, session advisory locks, holdable cursors, and SQL-level prepared statements are limited or unsupported. Protocol-level prepared statements are supported by the documented Neon configuration; do not apply the obsolete blanket claim that all prepared statements fail. Verify the exact driver/version combination. Direct connections are needed for persistent sessions and operations such as `pg_dump`. [Neon connection pooling, updated 2026-10-19](https://neon.com/docs/connect/connection-pooling)

**Architectural implications:** release database transactions before waiting on TMDB or the gateway. Budget local pool sizes across every process, replica and background worker, with room for migrations/administration; bound wait queues and acquisition timeouts. A local pool and Neon's pooler solve different lifecycle problems. Elastic container suspension/scale-out needs explicit connection management, rather than assuming an idle process reliably runs cleanup. [Neon elastic/serverless pooling guidance](https://neon.com/docs/guides/serverless-connection-pooling)

Neon can suspend inactive compute and reactivate it on a later query. Current documentation fixes five-minute inactivity suspension on the Free plan; paid plans can disable it. **Implication:** allow for wake-up and stale connections in connection/readiness budgets; do not turn published typical wake-up timing into an app latency guarantee. Exact plan, region, compute size, database version and availability expectations remain unknown. [Neon scale to zero, updated 2026-11-04](https://neon.com/docs/introduction/scale-to-zero)

**Verification before persistence implementation:** test TLS settings in the chosen driver/container; pooled transactions and protocol prepared statements; migration/administrative access; rollback and connection return after cancellation; reconnect after compute restart/suspension; pool exhaustion and timeout mapping. If PostgreSQL notifications are later used for live updates, reassess direct listener connections and connection budgets rather than assuming the pooled application connection can listen continuously.

## TMDB usage, operational limits and data lifecycle

**Directly observed current terms:** §1.C prohibits caching TMDB information longer than six months, creating derivatives, and use of TMDB APIs/content with an AI application, expressly including “in connection with, including for training”. §1.D requires purging TMDB content on license termination. §2 requires a written commercial agreement and gives examples including query-response systems and ML training/validation datasets. §3 requires logo attribution and a prominent nonendorsement notice. [TMDB API Terms of Use, §§1–3](https://www.themoviedb.org/api-terms-of-use)

**Architectural inference and unresolved scope:** these clauses raise a permission question for the proposed AI-enabled product and overview embeddings, even if a separate extraction step handles only user-supplied material. This report does not settle their legal interpretation or whether a different agreement applies. Obtain clarification/permission for the actual workflows before assuming TMDB content can be embedded, supplied to models, used in evaluation, or durably replicated. [TMDB API Terms of Use](https://www.themoviedb.org/api-terms-of-use)

Verification method: the research web fetch was denied by `robots.txt`; the official page was then opened successfully in a normal browser and its rendered terms read on 2026-11-07 UTC. No version/effective date was visible in the inspected page. This is a dated observation of a mutable source, not an account-specific license review.

TMDB's FAQ describes free noncommercial use with attribution; commercial use requires contacting TMDB. It requires an approved logo, less prominent than the application's, attribution in an About/Credits section, and a notice that the app is not endorsed/certified. It also says there is no SLA. The FAQ summary does not resolve the more specific terms above. Check the eventual agreement and final notice wording before release. [TMDB FAQ](https://developer.themoviedb.org/docs/faq)

TMDB disabled its historical 40-requests-per-ten-seconds limit in 2019. It currently describes an approximate upper limit around 40 requests/second that may change, and directs clients to respect `429`. This is not a stable quota entitlement, and the page does not establish a universal `Retry-After` guarantee. **Implication:** bound concurrent work, share rate control across replicas using the same upstream budget, back off on throttling, honor retry guidance when present, and avoid unbounded fan-out from imported titles or followed people's filmographies. [TMDB rate limiting](https://developer.themoviedb.org/docs/rate-limiting)

**Proposed data boundary, conditional on permitted use:** keep user actions separate from refreshable provider metadata; retain provider IDs, provenance, locale, fetch time and expiry/deletion state sufficient to enforce the eventual agreement. A metadata refresh or purge must not erase a user's watched/followed choices. Include derived indexes/embeddings, image copies, backups and exports in the data-use question rather than assuming they are exempt. Six months is a retention ceiling in the observed terms, not an appropriate freshness target for every field.

TMDB daily exports contain IDs and a few filtering attributes, not full metadata; they do not remove detail-fetch costs. Images are referenced by paths and require configuration-derived base URL/size information. Follow the supplied API mechanisms rather than treating an image path or an ID export as a complete owned catalog. [Daily ID exports](https://developer.themoviedb.org/docs/daily-id-exports), [Image URL basics](https://developer.themoviedb.org/docs/image-basics)

## Postgres search options without selecting one

| Option documented today | Capability and consequential boundary |
| --- | --- |
| `pgvector` (`CREATE EXTENSION vector`) on Neon | Stores supplied embeddings; supports exact/approximate nearest-neighbor queries and several distance metrics. Installed per database. Availability does not choose the embedding model or establish useful retrieval quality. [Neon pgvector](https://neon.com/docs/extensions/pgvector) |
| pgvector HNSW / IVFFlat | Approximate indexes trade recall for speed. Post-index filtering can return too few results; iterative scans are version-dependent. Benchmark the user's followed/seen/timeline filters, rather than global-catalog retrieval alone. [pgvector upstream filtering and index guidance](https://github.com/pgvector/pgvector#filtering) |
| Built-in `tsvector` / `tsquery` | Linguistic full-text matching and ranking are available without an embedding model; keyword relevance is a different retrieval signal from embedding similarity. [PostgreSQL text search](https://www.postgresql.org/docs/current/textsearch-intro.html) |
| `pg_trgm` | Trigram string similarity and index support can help title/name spelling and fuzzy matching; they do not by themselves implement semantic storyline retrieval. [PostgreSQL pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html) |
| Neon `lakebase_vector` / `lakebase_text` | Current docs expose ANN indexes compatible with pgvector types/operators and BM25 indexes over standard `tsvector`, respectively. `lakebase_vector` needs Postgres 16+ and its preloaded library. These are additional candidates, not a recommendation or portability guarantee. [lakebase_vector](https://neon.com/docs/extensions/lakebase-vector), [lakebase_text](https://neon.com/docs/extensions/lakebase-text) |

Current Neon documentation says `pg_search` support was deprecated for new projects on 2026-03-19 and removed from existing projects on 2026-09-21, with `lakebase_text` as its BM25 replacement. Older official announcements advertising `pg_search` on Neon are therefore insufficient evidence of current support. Recheck extension/version availability for the chosen Postgres version when implementation starts. [Neon pg_search retirement](https://neon.com/docs/extensions/pg_search), [Neon extension/version catalog](https://neon.com/docs/extensions/pg-extensions)

**Architectural inference:** keep semantic-query intent and authorized result filtering independent of any vector SDK. Track embedding model/version, dimensions, metric, source text/version and generation status so re-embedding can be planned. Exact versus ANN indexes and hybrid lexical/vector ranking can wait for a permitted corpus and representative latency/recall evaluation; model changes may require regenerating the corpus. No extension solves permission, relevance, or user-scope authorization automatically.

## Logfire and sensitive inputs

Logfire scrubs selected fields using patterns before export, but its current guidance explicitly exempts LLM message attributes from scrubbing. It recommends disabling message content capture for sensitive interactions. `include_content=False` excludes prompts/completions and tool arguments/results while retaining structural telemetry; it does not control custom spans, run metadata or separately captured HTTP bodies. **Implication:** default to metadata-only AI traces and separately review HTTP/database/application instrumentation. Do not rely on keyword scrubbing to protect arbitrary notes, photos or watch histories. [Logfire scrubbing guidance](https://logfire.pydantic.dev/docs/how-to-guides/scrubbing/), [Pydantic AI content-exclusion scope](https://ai.pydantic.dev/logfire/#excluding-prompts-and-completions)

URLs and SQL statement attributes can also escape ordinary scrubbing; use parameterized SQL and keep sensitive values out of URLs. Photo content needs explicit treatment: Pydantic AI's binary-content exclusion has limits for binary content nested in custom types. **Implication:** check exported spans with synthetic input before enabling production telemetry; capture timings, outcomes, request correlation, token usage when available, pool waits and throttle counts without user content. Retention, project access, region, cost and deletion settings remain deployment decisions. [Logfire scrubbing security tips](https://logfire.pydantic.dev/docs/how-to-guides/scrubbing/), [Pydantic AI binary-content instrumentation](https://ai.pydantic.dev/logfire/)

## Docker and deployment/runtime constraints

Docker's exec-form entrypoint allows the application to receive stop signals; shell-form entrypoints can prevent that. **Implication:** graceful shutdown must stop admission, drain or cancel work, close HTTP/DB pools, and flush bounded telemetry within the host's stop deadline. Container restarts still require a deliberate policy for interrupted imports or paid upstream work. [Dockerfile entrypoint and stop signals](https://docs.docker.com/reference/dockerfile/#entrypoint)

Compose starts dependencies when running by default, not when ready; health conditions are explicit. This helps local services but does not establish remote Neon/gateway readiness. Separate liveness from readiness and do not make every health probe perform a paid model call or trigger a provider request storm. Docker build secrets should use secret mounts; build arguments/environment instructions can persist sensitive material in the image. [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/), [Docker build secrets](https://docs.docker.com/build/building/secrets/)

**Deployment evidence still needed:** selected host's maximum request/body sizes, timeouts, memory/CPU, outbound connectivity, upload storage lifecycle, process/replica counts, shutdown grace, streaming/proxy behavior and any worker execution limits. Docker is packaging; these host properties determine whether a long-running extraction can remain request-bound. Python/async drivers do not decide durable work or client transport.

## Decision boundaries and revisit triggers

1. **Before assuming provider feasibility:** identify/document the LLM Gateway and establish permitted TMDB workflows. These are unresolved inputs; this research resolves neither.
2. **Before persistence contracts:** establish metadata ownership, refresh/expiry/purge behavior and user-data separation. Revisit when a provider agreement or additional data source changes retention and reuse rights.
3. **Before deployment sizing:** choose runtime/worker boundaries and budgets, then verify pooled/direct DB behavior, cancellation and connection recovery. Revisit at replica/worker growth or use of session-level Postgres features.
4. **Before production observability:** settle content exclusion and access/retention settings; inspect actual exported synthetic traces. Revisit when instrumentation, SDKs, captured bodies or new input types change.
5. **Before semantic-search implementation:** establish permitted source text and evaluate representative user-scoped retrieval. Defer embedding/model/index/hybrid choices until that evidence exists; recheck current Neon extensions then.

All live documentation links were inspected during this research. Where a page is rolling, this report records observed behavior rather than claiming compatibility with an unselected package or service version. No runtime interoperability or load test has been performed.
