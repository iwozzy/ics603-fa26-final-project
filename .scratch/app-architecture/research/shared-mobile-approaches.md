# Sharing web, iOS, and Android clients

Research date: 2026-11-06 (Pacific/Honolulu). Primary sources accessed that day. Scope: evidence for “Research approaches to sharing web, iOS, and Android code,” the main-checkout tracker ticket at `.scratch/app-architecture/issues/01-research-shared-mobile-approaches.md`; the tracker lives separately from this research branch. This report does not select a framework or settle what “native” means. The proposal describes a small multiuser movie-discovery app, photo/note imports, review screens, and a filmography timeline. No application implementation, sharing measurement, or device evaluation was performed.

## Findings that matter before choosing

Three supported rendering families offer substantial sharing, with four useful project arrangements to compare:

| Approach | Mobile rendering and native access | Practical sharing boundary |
| --- | --- | --- |
| Expo / React Native plus React Native for Web | React Native mounts platform host views; React Native for Web maps components onto React DOM primitives. Expo supplies cross-platform tooling and libraries. | TypeScript application logic and compatible React Native screens/components can span all three. DOM-only components and platform-only libraries require replacements or adapters. [React Native rendering](https://reactnative.dev/architecture/render-pipeline), [Expo web](https://docs.expo.dev/workflow/web/) |
| Separate React DOM web and React Native mobile apps in one repo | Web keeps DOM UI; mobile uses React Native host views. | Framework-independent TypeScript logic and compatible React code can be shared; DOM screens do not automatically render on mobile. This is an inference from the rendering boundary, not a promise of automatic migration. [Expo web](https://docs.expo.dev/workflow/web/) |
| Flutter for all three | A Dart widget tree is rendered by Flutter's engine. Native services are available through plugins/platform channels; embedding individual native controls is possible. | Dart application logic and widgets can span targets; platform plugins, imports, responsive layouts, and embedded platform views introduce differences. [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [platform integration](https://docs.flutter.dev/platform-integration) |
| Web application plus Capacitor | Web UI remains web UI inside a native container; iOS uses WKWebView. Plugins provide native capabilities. Ionic is an optional web UI toolkit, not a requirement. | Existing JavaScript/TypeScript, HTML, and CSS can remain the common UI. Native configuration, plugin behavior, permissions, and mobile interaction still require work. [Capacitor introduction](https://capacitorjs.com/docs), [iOS runtime](https://capacitorjs.com/docs/ios), [UI guidance](https://capacitorjs.com/docs/getting-started/ui) |

“Native” therefore needs at least three separate answers: app-store installation, access to native capabilities, and use of operating-system UI controls. Flutter and a WebView wrapper can satisfy the first two without having the same rendering model as React Native. A requirement for platform views would materially narrow the options; a requirement for camera access alone would not. This distinction is an interpretation of the mechanisms above, not a framework ranking.

The reviewed sources establish sharing mechanisms, not a defensible percentage for this project. No “90% shared” estimate is warranted without representative screens, dependency choices, and device checks. One repository also does not imply one language, one deployment, or identical UI on each platform.

## Expo and shared React options

Expo supports both universal React Native components and web-only React DOM components. React Native for Web wraps browser primitives, while DOM-only elements do not render on native platforms. Platform file extensions permit web, iOS, Android, and native implementations behind common imports. This creates an explicit escape hatch when a timeline, navigation shell, or photo adapter needs platform behavior. [Expo web](https://docs.expo.dev/workflow/web/), [platform-specific modules](https://docs.expo.dev/router/advanced/platform-specific-modules/)

Expo Router provides file-based navigation across Android, iOS, and web. Its route structure can be common while layouts vary by platform; platform-specific route files require a fallback route so universal deep links remain defined. A shared route is therefore possible without requiring the same desktop sidebar and mobile tab layout. [Router introduction](https://docs.expo.dev/router/introduction/), [platform-specific modules](https://docs.expo.dev/router/advanced/platform-specific-modules/)

Expo supports workspace monorepos and automatically configures Metro when its supported configuration is used. Its own guide cautions that additional apps/packages increase tooling complexity. **Inference for this repo:** a Python backend directory plus one universal client is already one repository; extracting many frontend packages or creating separate web/mobile apps can wait until there is a concrete need. [Monorepo guide](https://docs.expo.dev/guides/monorepos/)

Native project maintenance can use Continuous Native Generation: configuration and config plugins generate iOS/Android projects. Manual edits in generated directories can be lost by a clean prebuild. This reduces checked-in native boilerplate but makes dependency/config-plugin compatibility an ongoing maintenance concern. Hosted Expo Build/EAS can build and sign binaries; local builds are also supported. [CNG](https://docs.expo.dev/workflow/continuous-native-generation/), [build service](https://docs.expo.dev/build/introduction/)

Expo websites can be self-hosted or deployed through third parties. Static output generates route HTML; server output needs a rendering server, while a single-page output can use static hosting. **Inference:** the preference for a Python backend does not require adopting Expo API routes or a JavaScript application backend; choose web output deliberately to avoid accidentally adding a second server responsibility. [Publishing websites](https://docs.expo.dev/guides/publishing-websites/)

**Incremental-adoption consequence:** beginning with React DOM preserves a later shared TypeScript core, but those DOM screens need rewriting or explicit web-only treatment for React Native. Beginning with universal components makes UI sharing available earlier but constrains initial component/library selection. Both statements follow from Expo's documented DOM/native rendering boundary; neither establishes which cost is preferable here. [Expo web](https://docs.expo.dev/workflow/web/)

## Flutter

Flutter supports iOS, Android, and web from a common codebase, with plugins or custom integrations for platform features. Its UI is engine-rendered rather than a collection of ordinary OS controls; embedding native controls uses platform views and adds composition/synchronization overhead. **Inference:** Flutter can meet a “native installed app” requirement, but requires a different discussion if the requirement is specifically UIKit/Android controls throughout. [Platform integration](https://docs.flutter.dev/platform-integration), [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview)

Flutter's own web guidance positions it for app-centric experiences, including SPAs and PWAs, and warns that its output does not meet search engines' indexing needs in the same way as document-oriented HTML. **Inference for this app:** a signed-in timeline/review interface fits the stated application category; public indexable movie/person pages or substantial reading content would need an explicit web strategy, potentially separate HTML content. [Flutter web FAQ](https://docs.flutter.dev/platform-integration/web/faq)

Flutter's Router supports deep links and browser address synchronization; the docs recommend a routing package such as `go_router` for advanced cases and discourage named routes for most apps, including because named routes do not support browser forward navigation. Cross-platform navigation is available but still needs a deliberate setup. [Navigation](https://docs.flutter.dev/ui/navigation)

Web deployment produces a build directory usable by a web server. iOS release builds require Xcode/macOS in the documented local workflow; Android builds have their own signing, manifest, and Gradle configuration. Flutter can also be embedded piecemeal into existing native or web apps through add-to-app. **Inference:** add-to-app makes partial replacement possible, but for a small greenfield product maintaining mixed UI runtimes would add integration work rather than eliminate a framework migration. [Web release](https://docs.flutter.dev/deployment/web), [iOS release](https://docs.flutter.dev/deployment/ios), [Android release](https://docs.flutter.dev/deployment/android), [add-to-app](https://docs.flutter.dev/add-to-app)

## Web plus Capacitor

Capacitor can be added to an existing modern JavaScript web application. It requires a package manifest, a built-assets directory, and a root `index.html`; its workflow builds the web assets, syncs them into native projects, then builds/runs through native tooling. **Inference:** a client bundle talking to the Python API is a straightforward fit; a server-rendered Python website is not automatically a packageable mobile client merely because it runs in a browser. [Installation requirements](https://capacitorjs.com/docs/getting-started), [workflow](https://capacitorjs.com/docs/basics/workflow)

Capacitor's UI guidance explicitly says a good mobile experience takes more than wrapping a website. Ionic can provide platform-convention components, transitions, and routing for React, Vue, or Angular, but is optional. **Inference:** this path can defer native packaging with limited initial infrastructure, provided wrapped web UI is acceptable; it does not defer responsive design, keyboard behavior, safe-area layout, or mobile usability indefinitely. [UI guidance](https://capacitorjs.com/docs/getting-started/ui)

Universal/App Links can open installed apps or fall back to the website. Capacitor exposes an app URL event that the application's chosen web router handles, and requires website/app association configuration. It does not replace the web router with a universal screen model automatically. Native iOS development requires macOS/Xcode or an appropriate cloud build service; Android has its own toolchain. [Deep links](https://capacitorjs.com/docs/guides/deep-links), [environment setup](https://capacitorjs.com/docs/getting-started/environment-setup)

## Photo imports and accessibility

| Concern | Evidence and consequence |
| --- | --- |
| Expo camera/library | `expo-image-picker` supports Android, iOS, and web for library selection or camera capture. Web calls need immediate user activation and have cancellation inconsistencies. Android can destroy the activity while picking; the library exposes pending-result recovery. A common API does not remove lifecycle differences. [ImagePicker](https://docs.expo.dev/versions/latest/sdk/imagepicker/) |
| Flutter camera/library | Flutter's maintained `image_picker` package supports the target platforms. Its docs call for iOS usage descriptions and Android lost-data recovery; the web implementation follows browser capabilities and restrictions. [image_picker](https://pub.dev/packages/image_picker), [web implementation](https://pub.dev/packages/image_picker_for_web) |
| Capacitor camera/library | The official Camera plugin supports capture and choosing existing photos. iOS needs usage descriptions; Android restoration events recover data after the OS terminates the app during capture. Web gallery selection uses a file input; web capture can use PWA Elements with a file-picker fallback. [Camera plugin](https://capacitorjs.com/docs/apis/camera) |
| React Native accessibility | React Native provides VoiceOver/TalkBack integration, with platform differences. React Native for Web uses HTML/ARIA semantics and browser keyboard focus; its docs distinguish web `tabIndex` from native accessibility/focus props. Accessibility code can be shared in part, but needs platform verification. [React Native](https://reactnative.dev/docs/accessibility), [React Native for Web](https://necolas.github.io/react-native-web/docs/accessibility/) |
| Flutter accessibility | Standard widgets generate a semantics tree, customizable through `Semantics`. The web docs describe an accessibility activation step or programmatic enabling, and list supported browser/screen-reader combinations. Include semantics and browser interaction in any later evaluation rather than inferring accessibility from the rendered appearance. [Assistive technologies](https://docs.flutter.dev/ui/accessibility/assistive-technologies) |
| Wrapped-web accessibility | Web content retains HTML/ARIA responsibilities: meaningful regions, headings, and structure support screen-reader and keyboard navigation. The fact that the container is installable is not evidence that its screens are accessible; testing the actual WebView and devices is a project validation task. [W3C WAI structure guidance](https://www.w3.org/WAI/tutorials/page-structure/), [Capacitor iOS WebView](https://capacitorjs.com/docs/ios) |

**Application-level inference:** a photo-input port should return a normalized app-owned asset description and explicit selected/cancelled/failed outcomes, hiding URI/file/blob/plugin details in platform adapters. Keep the review edits and accepted import state outside the picker component. Define what survives picker interruption and app restart. Test actual image bytes and orientation on target devices before relying on camera behavior for DVD photos or collection screenshots; this research did not establish image fidelity.

## Ports and adapters, without speculative infrastructure

The following are architectural deductions from the platform boundaries, not requirements imposed by the frameworks:

- Keep frontend use cases and state transitions for following people, reviewing extracted titles, and filtering a timeline independent of UI components and platform plugins. Provide small ports for the application API, photo acquisition, session persistence, and navigation where those boundaries actually differ.
- Keep DTO parsing/validation at the network adapter. Python/Pydantic models do not execute directly in TypeScript or Dart clients; shared API schemas and compatible client types are a different kind of sharing from shared runtime code. Deciding the client language does not require moving the Python extraction, TMDB integration, database, or AI orchestration into the client.
- Treat storage, authentication redirects, permissions, and notification delivery as platform adapters. Browser and installed-app behavior should be specified when those features become real; avoid assuming one storage or authentication mechanism transparently works everywhere.
- A repository may contain `backend/` and `client/` initially. Multiple client packages, a general plugin abstraction, and separate web/native apps are optional developments. A module boundary is enough until extraction solves an observed problem.
- Docker can package the backend and web-serving responsibilities. It does not remove the separate iOS native build environment: Expo's build infrastructure uses macOS for iOS, Flutter's local guide requires macOS/Xcode, and Capacitor documents the same toolchain distinction. [Expo build environments](https://docs.expo.dev/build/introduction/), [Flutter iOS](https://docs.flutter.dev/deployment/ios), [Capacitor setup](https://capacitorjs.com/docs/getting-started/environment-setup)

No researched client approach inherently settles HTTP versus WebSocket contracts, durable jobs, Python async execution, Neon, Logfire, or model choice. Those are separate architecture questions. This report makes no latency, performance, operational-cost, or maintainability ranking from documentation alone.

## Decisions for the human and reversal costs

These are decision inputs, not a recommended selection:

| Decision to resolve | Why it changes the choice | Cost of reversal / useful deferral trigger |
| --- | --- | --- |
| Does “native” mean installed apps and capabilities, OS controls, or a polished platform-conforming experience? | Determines whether all three rendering families qualify. | Rendering-family changes usually replace screens, styling, navigation, and platform integration. Resolve before substantial UI work. |
| Is the first web product a signed-in application, public indexable content, or both? | Flutter documents web indexing limits; Expo offers multiple web rendering outputs; Capacitor packages web assets. | Public HTML pages can be separated later, but discoverable movie/person URLs and web behavior need deliberate design before a large screen catalog develops. |
| What sharing matters: logic, UI components, whole screens, or identical behavior? | Universal React Native, separate React apps, Dart widgets, and a shared WebView optimize different boundaries. | Pure TypeScript logic can survive a React DOM/React Native split; framework-dependent UI generally cannot. A Dart transition also entails porting language-specific client logic. These are deductions from the documented runtimes. |
| Can mobile shipping wait, and which platform behaviors must V1 preserve? | Web-first Capacitor adoption differs from choosing a universal UI model at the start. | Native signing/build automation can wait until a mobile delivery milestone. Revisit earlier if camera reliability, deep links/authentication, notifications, or native UI requirements become acceptance criteria. |
| How much platform-specific work is acceptable? | All sources expose native configuration and behavior differences. | Keep narrow seams now. Measure sharing only after a later authorized slice exercises timeline navigation, editable extraction review, and photo import on browser, iPhone, and Android. No prototype is part of this ticket. |

This evidence leaves the framework choice open. The consequential commitment is the client rendering/language family; backend service boundaries and app-owned frontend use cases can reduce the amount of work coupled to that commitment.
