## Question

What Docker-based deployment topology and operational controls are justified by the quality targets and selected architecture? Decide where async API execution, any durable/background work, Neon connections, secrets, migrations, and external-provider budgets live. Define how Logfire spans requests/jobs/provider calls while handling sensitive content, and where global API rate limits, LLM usage budgets, TMDB limits, timeouts, and failure recovery are enforced. The user explicitly requires a global rate limit for each API. Defer hosting details only where doing so preserves the architecture and records a revisit trigger.

## Answer

Resolved through human discussion on 2026-11-09 (Pacific/Honolulu).

### Choices and rationale

**Start with one Dockerized backend deployment and managed Neon/Logfire.** Keep containers replaceable, durable application data in Neon, secrets supplied through deployment configuration, and schema migrations as a controlled release step. Retain the modular backend and independently configured capability adapters. Hosting provider, web-serving arrangement, process count, connection-pool sizing, and placement of off-request embedding preparation follow implementation. The import and suggestion workflows remain request-scoped; movie preparation remains outside live search without requiring a durable queue. Add services only for a concrete need. Verify the provisional $25/month total envelope and actual client-facing HTTP/2 before deployment; neither cost nor provider capability is established by this planning decision.

**Global per-API rate and usage limits.** Apply controls across visitors, tasks, and serving processes, distinguishing incoming application requests from outgoing provider/gateway calls. Include retries and background preparation in outgoing enforcement. Each API has both rate limits and cumulative usage limits. Once its usage limit is exhausted, initiate no new usage of that API until the limit is increased; do not assume periodic automatic replenishment. The purpose now is simple protection against abuse and vandalism, not exact billing enforcement. App-owned controls supplement upstream quotas/budgets and do not depend on a gateway exposing a remaining-budget endpoint. Different configured gateways retain their own quota/error semantics. Keep unrelated available workflows usable when a provider-specific operation is blocked, subject to those workflows' own limits.

**The application asks only whether a new request is permitted now.** Put admission/accounting behind application-owned ports and adapters. Domain and feature logic do not inspect counters, thresholds, storage, or synchronization rules. Concrete policy and future changes remain replaceable behind this boundary. Entry adapters enforce incoming controls; provider/gateway integration enforces outgoing admission before initiating calls. The exact API/quota-key mapping, accounting units, configured limits, and operator mechanism to raise them follow implementation.

**Decide from memory; persist usage asynchronously.** Admission must not wait for a durable-store read/write. Account for admitted/in-flight requests in memory immediately, then persist usage asynchronously and refresh future admission information. Retain durable totals across restarts and initialize admission state from them rather than treating a restart as a new allowance. All serving/preparation processes contribute to shared global totals; independent process-local budgets must not multiply the configured allowance. The initial policy accepts approximate enforcement: in-flight work, delayed cross-process updates, and unpersisted recent usage after a crash can produce overshoot. Select acceptable update/persistence delays before release. This decision does not require exact distributed quota coordination, a particular counter store, or an extra service. Revisit stronger guarantees if observed overshoot becomes a practical problem.

**Refuse promptly at capacity and communicate through HTTP.** Bound concurrent expensive work and interactive waiting. When admission is denied, return an HTTP status to the client; exact status/code mappings and user-facing presentation remain deferred. This explicitly refines the semantic-search/suggestion guidance allowing empty results on other service failures: admission refusal must still be communicated through HTTP. Background preparation may wait for a later opportunity under its eventual scheduling policy; no unbounded interactive waiting or durable queue is implied. Align proxy/request deadlines with configured operation/retry bounds during implementation. Account for retry attempts under the same outgoing controls, respecting terminal upstream failures.

**Instrument operations and external calls with bounded, restricted telemetry.** Keep Logfire dependencies outside domain/application logic. Capture timings, outcomes, usage, and correlation identifiers, including off-request preparation and deliberately empty results on service failure. Log suggestion results as explicitly authorized in [Define recommendation inputs and trusted-result boundaries](14-recommendation-architecture.md#answer). Restrict operational logs to maintainers and give them finite retention. Exclude raw notes/photos, prompts, credentials, and other content not explicitly authorized. Choose exact redaction, retention, alerting, and sampling settings before release; verify actual configuration rather than enabling unrestricted automatic content capture. Telemetry remains separate from saved user activity and suggestion history.

**Use the simplest verified backup/restore arrangement.** Prefer managed-database facilities where sufficient, select exact retention and recovery targets during deployment implementation, and perform a restore check before release. Preserve confirmed user data while excluding raw import inputs from backups. Restoration must respect applicable user deletions, revoked access, and provider-data cleanup, preserving app-owned identities/activity independently of provider metadata and derived representations. Carry existing retention/attribution and model no-training requirements into release configuration without reopening the settled provider-use decision. Additional recovery infrastructure requires a demonstrated need.

### What must be fixed now

Keep the deployment simple and containers replaceable; separate durable state, runtime secrets, and release migrations. Require global per-API rate/usage controls behind an allowed/denied capability, memory-based admission with immediate in-flight accounting, asynchronous durable usage updates, accepted approximate enforcement, and explicit HTTP refusal. Preserve restricted finite-retention observability with the suggestion-result exception, verified recovery, temporary-input cleanup, and the established ownership/provider boundaries.

Revisit deployment sizing/topology when measured ordinary browsing persistently misses the roughly one-second target under normal conditions, forecast total cost exceeds the provisional $25/month envelope, or sustained resource rejection/failed preparation undermines intended workflows. Exact monitoring windows and thresholds follow implementation. Recheck course-gateway availability/funding before relying on it beyond the course. No new prerequisite research ticket is needed to resolve this architecture direction; concrete implementation and provider-capability checks remain explicit follow-up work.

### Cost of reversal

Hosting, limiter/accounting technology, telemetry configuration, and preparation scheduling remain replaceable behind the agreed boundaries, with deployment or stored-state migration where needed. Tightening quota precision may require stronger coordination and a different latency trade-off, so do not present approximate caps as exact spend guarantees. Putting counters/policy into domain logic, relying on disposable container state for durable records, or logging raw inputs would make later changes more expensive. Those responsibility boundaries are fixed now; specific vendors, tools, and recovery values remain deferred.
