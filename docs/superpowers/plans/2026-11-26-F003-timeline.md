# F003 Timeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Discover distinct movies from followed people through a bidirectional Timeline, populated by independently queued filmography hydration and retained across navigation.

**Architecture:** Preserve existing ports, application use cases, persistence adapters, and the OpenAPI-generated client boundary. Hydration uses an in-process bounded pipeline, shared admission, and its own database pool; timeline reads query local catalog data with keyset cursors. A framework-free client store retains pages and a visible movie anchor, refreshing a bounded neighborhood on route entry.

**Tech Stack:** Python 3.13+, FastAPI/Pydantic, SQLAlchemy async/psycopg/PostgreSQL/Alembic, HTTPX, TypeScript, Expo Router/React Native Web, Zod/Hey API, pytest/Jest/Playwright. No new dependencies.

**Spec:** [Approved Timeline design](../specs/2026-11-25-F003-timeline-design.md), approved 2026-11-26. Read it before this plan. This plan defines implementation interfaces; the spec governs behavior.

## Global Constraints

- Keep both cores framework-free. Vendor DTOs and generated API types stay in adapters; transactions are committed by application use cases.
- New IDs: `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. Movie IDs cross the API as positive JSON integers in `1..9007199254740991`; dates remain calendar-date strings in the client.
- Hydration: `movie_hydration` pool with **5 connections plus 5 overflow**; **1,024 outstanding distinct people**; **ten active person jobs**; **at most ten request starts in any rolling one-second window**; **at most ten concurrent provider requests**.
- Freshness: **24 hours**, exactly 24 hours old eligible; no DB transaction across provider I/O. Queue independently of successful follow commit.
- Three provider attempts and three database attempts, each **five seconds**; ordinary retry delay **one second**; response bound **10 MiB**; shutdown drain **five seconds**. Database retries retain the payload and incur no provider charge.
- Every provider attempt uses the existing shared accounting instance and first-requester guest/IP context. Local reads, skips, coalesced requests, and DB retries consume no provider allowance.
- Every hydration `429` pauses all hydration dispatch for **at least 60 seconds**, honoring a valid longer integer/HTTP-date `Retry-After`. Already in-flight requests may finish. No post-cooldown burst.
- Upsert-only, one transaction and one statement per target table; preserve both cast and crew credits for the same movie. Person timestamp advances atomically; movie complete-credit timestamp stays null/unchanged.
- Timeline limit **1–100**, default **20**; anchored refresh returns up to **2 * limit**; UTC today belongs to the past side. One SQL statement per response includes clock/boundary/availability work.
- Timeline uses guest ownership, `no-store`, empty `500` failures, seven-second server/eight-second transport deadlines. Cursor JSON is unsigned, versioned, validated, and limited to **1 KiB** encoded input.
- No TanStack Query, durable jobs, backfill/scanner, polling, refresh button, Now divider, search/filters/ruler, cache persistence, or page eviction. Refresh on route entry/reload; retain data and movie/offset across navigation.
- Sidebar order: Search, Timeline, Following. Display English month/year, for example `August, 2022`, without shifting calendar dates to local time.
- Follow `AGENTS.md`. Use the fixed disposable database harness and synthetic provider fixtures; do not inspect operator configuration or credentials, and never use live provider traffic in tests.

## Review Focus

- Same person/movie in cast and crew, including repeated jobs: save every distinct credit and show one movie (Tasks 2, 3, 6, 11).
- Initial past side empty but future movies available: preserve the future cursor and accept mouse, keyboard, and touch intent without an eager mount request (Tasks 6, 9, 10, 11).
- Overlapping `429` responses, long HTTP-date waits, cancellation, or accounting exhaustion: extend the shared cooldown, avoid premature charges, and finish shutdown without late admission (Tasks 4, 5).
- Moving release dates, vanished anchors, and user scrolling while return refresh is in flight: retain the user's current position and ignore obsolete results (Tasks 6, 9, 10, 11).
- Guest creation or route departure during concurrent paging: old responses must not populate the new guest/window or erase retained data (Tasks 8, 9, 11).
