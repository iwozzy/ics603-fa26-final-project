# Durable guest identity

Approved in conversation on 2026-11-15: replace 24-hour guest sessions with a durable guest profile reached through a persistent, renewable opaque cookie. Returning with the same valid cookie preserves the profile regardless of elapsed time. Missing/unknown credentials create a fresh profile; lost cookies have no automatic recovery.

## Approaches

We considered the existing expiring sessions, durable profiles with persistent opaque credentials, and signed tokens. The user selected durable profiles with opaque credentials. Server-issued proof validation and digest lookup remain; a separate expiring session is unnecessary for this guest flow.

## Design

- The cookie is HttpOnly, same-site lax, path `/`, secure on HTTPS, and has `Max-Age=31536000` (365 days). Every successful bootstrap reissues the same valid value with a renewed browser lifetime, or issues a fresh value for a new identity. Browser deletion/eviction may lose identity independently of server retention.
- The existing cookie name, `/api/v1/guest-session` endpoint and OpenAPI operation ID remain compatible. Internal domain/application types describe guest identity/bootstrap instead of an expiring session. `GuestContext` contains only profile ID and the current request's IP key.
- Rename `guest_sessions` to `guest_credentials`, retain its surrogate ID, profile foreign key, and unique digest; remove server expiry. Lookup maps digest to immutable `StoredGuestIdentity(profile_id)` without an expiry filter. Existing mappings, including rows past their former expiry, become durable; no profiles or proofs are regenerated by migration.
- Subsequent amendment approved on 2026-11-15: the cache uses only its 10,000-entry LRU capacity, with no TTL or time dependency. Positive entries remain until eviction or worker restart; database credential deletion/mapping changes can remain unobserved indefinitely for a hot entry. Cold workers and misses validate against Postgres. Bootstrap still checks authoritative storage and its IP limiter; cache publication happens only after successful transaction exit.
- Admission uses `guest` counter scope keyed by profile ID. Existing `SESSION_*` configuration and `UsagePolicy.session_*` field names remain compatible, now supplying the per-guest limits. Global/IP limits and atomic admission remain unchanged.
- Migration aggregates mapped legacy session counters per profile/feature/window into guest counters and removes the mapped legacy counters, preserving recorded usage. Unknown/orphan legacy counters remain stored. Existing attempt records retain their historical key context. Migration runs with application writes stopped, as part of deploying the schema and matching backend together.
- Downgrade restores expiring sessions with 24 hours from rollback time. It assigns each mapped guest aggregate to a deterministic credential ID, preserving total recorded usage while restoring the older per-session policy. Upgrade/downgrade tests verify count preservation, including multiple credentials for one profile.

## Verification

Test returning after 48 hours and one year using warm and cold caches, cookie renewal without identity/token changes, guest quotas persisting across bootstrap and multiple credentials, profile/IP separation, invalid proof handling, and database outage behavior. Real migration tests seed the previous schema, verify durable resolution of previously expired credentials, aggregate all windows, and check downgrade/re-upgrade preservation. Run complete backend tests, type/lint/import checks, browser flows, and a fresh code review. Preserve prior uncommitted admission/cache changes.
