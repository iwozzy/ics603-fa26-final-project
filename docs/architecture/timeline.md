# F003 movie timeline

A guest discovers movies through the credits of people they currently follow. Search writes people in the background, Follow schedules filmography hydration, and Timeline reads the shared catalog through the guest's current memberships. The approved design records the data model, query examples and delivery guarantees. [F003 design](../superpowers/specs/2026-11-25-F003-timeline-design.md)

## From Follow to a stored filmography

The HTTP adapter checks origin, identity and guest ownership. The application use case enqueues a valid person and the originating guest context before opening its following unit of work. Enqueue performs no I/O. The follow transaction still locks the profile, inserts the membership, reads the snapshot, enforces the cap and commits before returning. Hydration can run even if that commit fails or the follow is already present. Unfollow changes membership and leaves accepted work and the catalog intact. A later explicit follow can submit work again.

The composition root wires three database pools. Guest operations, following, accounting and timeline reads use `application`. The best-effort search summary writer uses `people_writer`. Filmography freshness reads and writes use `movie_hydration`, with five connections and five overflow. Every hydration database attempt gets its own unit of work. A freshness read completes before any provider request. A missing timestamp or one at least 24 hours old permits a fetch. The worker rechecks freshness before a provider retry.

Within one backend process, the hydrator coalesces up to 1,024 outstanding distinct people and runs up to ten active jobs. The first accepted guest and IP own the charge for each actual provider attempt, including retries. Search and hydration share one usage admission service. The hydration dispatcher gates starts to ten in any rolling second and ten concurrent requests. It checks cooldown, shutdown, concurrency and rate capacity before admitting and starting the provider call. Waiting, coalescing, fresh skips, timeline reads and database retries consume no provider allowance. Multiple backend replicas would require coordination of these process-local gates and accounting.

A hydration 429 extends a shared monotonic deadline by at least 60 seconds from receipt. A longer valid integer or HTTP-date Retry-After extends it further. In-flight calls may finish and later 429s can extend the wait. The rolling start limit applies when dispatch resumes. The pipeline allows three provider attempts with five seconds per attempt, a one-second ordinary retry delay and a 10 MiB decompressed response limit. The outbound TMDB adapter validates the requested person and maps distinct dated cast and crew credits from the appended movie credits into domain values.

A nonempty filmography uses one person upsert, one movie upsert and one credit upsert in a single transaction. An empty filmography needs only the person upsert. The application commits the accepted rows and the person's hydration timestamp together. Each distinct provider credit survives, including separate roles and jobs for one person on one movie. Omissions preserve existing rows, and person hydration leaves the movie's complete-credit timestamp untouched. Database retries reuse the normalized payload for up to three five-second attempts with a one-second retry delay.

Accounting starts before hydration accepts work. Shutdown closes intake and allows five seconds for accepted jobs to drain under the normal gates. The hydrator then closes dispatch, cancels and awaits residual jobs. Accounting and the people writer drain before the shared HTTP client and database pools close. Process loss, saturation and exhausted retries can discard a job. Recovery depends on a later follow. Existing follows receive no startup backfill.

## Reading a guest's neighborhood

The FastAPI route resolves the guest and passes a domain request to the timeline use case. The PostgreSQL adapter returns a window in one SQL statement, including UTC calendar date and availability. An eligibility probe joins credits to the guest's follows for each candidate movie. Overlapping people and roles yield one movie. Results sort by descending release date and numeric local movie ID, which crosses the API as a positive JavaScript-safe integer.

The initial page starts at UTC today, inclusive. A future-boundary cursor can exist even with zero initial movies. Directional reads seek strictly past the cursor and include up to one page in descending display order. An anchored read includes the anchor on its older side and returns up to one page per side. The default page size is 20 and the accepted range is 1 through 100. Initial and anchored responses carry `as_of`. Directional responses leave it null. Cursors are unsigned, versioned base64url JSON, limited to 1 KiB of encoded input. The codec checks the field set, date, ID, kind and guest scope. The query independently enforces ownership against current follows. The endpoint uses `no-store`, empty 500 failures and a seven-second server deadline. The client has an eight-second transport deadline.

## Retaining the visible movie

The outbound client adapter validates the API response and maps it into plain TypeScript values. One application-level store owns timeline pages, cursors, guest generation and the visible movie's ID, calendar date and pixel offset. The Timeline UI measures virtualized rows and supplies their offsets. Calendar dates render directly as English month/year. A fixed poster slot reserves space during image loading.

A fresh visit loads the past window. Upward wheel, key or touch input can open the future edge even when the past side cannot scroll. Prepends restore the measured row. On departure the store retains its window in memory. On return it shows the retained neighborhood and requests one anchored refresh. A surviving movie keeps its offset. A removed anchor selects the nearest surviving at-or-older movie, or the closest newer movie if only newer movies remain. User movement during a return read supersedes it and permits one replacement after scrolling settles. Aborted and obsolete responses cannot replace the current window. New guest creation clears the store. Reload starts at the present. Hydration finishes independently of the screen and becomes visible on ordinary route entry or reload.
